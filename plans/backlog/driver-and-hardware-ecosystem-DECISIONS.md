# Decisions — driver-and-hardware-ecosystem implementation

> These resolve the open questions and unclear-bits flagged in
> [driver-and-hardware-ecosystem.md](driver-and-hardware-ecosystem.md)
> §"Open questions" and the pre-implementation review. Each decision is
> committed at the start of implementation; later phases may add follow-ups.

Implementation date: 2026-04-27

---

## I1 — `hardware-status.yaml` lives at `docs/hardware-status.yaml`

Resolves OQ #1 ("`docs/` vs repo root").

The existing `pull-driver-docs.mjs` copies the entire `docs/` tree
verbatim. Putting the YAML at `docs/hardware-status.yaml` means zero
puller changes — VitePress ignores `.yaml` for routing, so the file
quietly rides along to `thermal-label.github.io/docs/<repo>/hardware-status.yaml`
where the docs-site build script reads it.

Repo-root would have required a second pull pass and a config change.
No upside to justify it.

## I2 — Validator is per-driver `scripts/validate-hardware-status.mjs`

The plan hedges between per-driver and a "shared place." Per-driver
wins for v1: there are three drivers, the script is small (~80 LOC),
and a shared package (npm-published or git submodule) is overhead we
don't need yet. If a fourth driver lands and the validators have
drifted, *that's* the moment to factor out — not before.

Each driver repo gets its own copy. The reference implementation
lives in this repo at `CONTRIBUTING/hardware-status-schema.md` with
the canonical schema; the validator script source is duplicated
across drivers but the schema doc is the single source of truth.

## I3 — DEVICES sync is manual on docs-site bumps

Resolves the §B hedge ("CI auto-bump or manual?").

The docs site already pins `@thermal-label/<driver>-core` versions in
its `package.json`. Bumping is a one-line edit + lockfile regen; the
existing release process already requires the maintainer to run
`docs:build` after a driver release. We document the bump in the
release process and don't add CI machinery.

If this becomes annoying after a few cycles, F2-style automation can
take over. Until then, simple wins.

## I4 — `name` in YAML is a write-through cache; validator enforces match

The schema duplicates `name` from `DEVICES` for offline lookup
(scanning the YAML without importing the package). To prevent drift
the validator imports the driver's `DEVICES` and asserts
`yaml.devices[i].name === DEVICES[byPid].name`. A mismatch fails the
validator (and therefore the pre-push hook).

This makes `DEVICES` the canonical source of truth for `name` while
keeping the YAML readable standalone.

## I5 — Per-driver fragment via VitePress markdown include

Resolves §C ambiguity ("VitePress include or injection").

The build script writes a `_status-fragment.md` next to each
per-driver hardware page. The per-driver `docs/hardware.md` (which
the puller copies into the docs site) ends with a VitePress include
directive: `<!--@include: ./_status-fragment.md-->`. The fragment is
generated by `build-hardware-page.mjs` after the puller runs, so it
slots in cleanly without the puller needing to know about it.

Drivers don't need to ship the fragment themselves — the docs-site
build creates it post-pull. The include is a no-op (renders nothing)
when run outside the docs site, so per-driver `pnpm build` doesn't
break.

## I6 — Untested-device visibility lag is documented, not solved

A device added to `DEVICES` between driver releases is invisible on
the unified page until the docs site bumps deps. Fine for v1 — major
device additions warrant a release anyway. Documented in
`CONTRIBUTING/maintainer-runbook.md` under "Adding a device."

## I7 — Self-verification by maintainers is valid v1 seed

The plan's premise is community-driven verification, but the system
needs a starting point. Maintainer bench results are accepted as
v1 reports and marked with `selfVerified: true` on the report so
readers can weigh them appropriately. This is documented in both the
verification guide and the maintainer runbook.

## I8 — Status reporter handles are stored verbatim

`reports[].reporter` is the GitHub `@handle` from the issue. We do
not store email or other PII. If a reporter requests removal we
edit the YAML to anonymise the handle (`@anonymous-1` etc.) but
preserve the report row for the historical record.

## I9 — Phase 2 uses pinned versions; build script reads from node_modules

`build-hardware-page.mjs` resolves DEVICES via
`@thermal-label/<driver>-core` (already in the docs site's deps)
rather than parsing source TS. Aligns with I3 and avoids AST
parsing complexity.

## I10 — Cosmetic fix: example PIDs in the plan don't match reality

The plan uses `0x209d` for QL-820NWB and `0x1001`/`0x1002` for
LabelManager PnP. Reality (per `DEVICES` in each driver):
- QL-820NWB → 0x20a7 (0x209d is QL-820NWBc)
- LabelManager PnP → 0x1002

The seeded YAML files use real PIDs. The plan's prose isn't edited.
