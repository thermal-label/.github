# Docs conventions

The user-facing documentation site at [thermal-label.github.io](https://thermal-label.github.io)
is **single-source**: it pulls each package repo's `docs/` folder at build time
and stitches the result into one VitePress site. Per-repo VitePress configs do
not exist anymore.

This file is the contract your repo's `docs/` folder must satisfy.

## Required files

```
docs/
  index.md                  Required — package overview, picked up at /<repo>/
  getting-started.md        Required for drivers + CLI
```

If `index.md` is missing, the docs site build **fails**. Other files are
optional — the build picks up whatever markdown is there and skips quietly
when expected files are missing.

## Conventional files

```
docs/
  index.md                  Landing — what is this package, who is it for
  getting-started.md        Install + smallest working snippet
  core.md                   Protocol-layer reference (drivers)
  node.md                   Node integration guide (drivers)
  web.md                    Browser integration guide (drivers)
  hardware.md               Supported devices (drivers)
  api/                      Generated by `pnpm docs:api` (typedoc), committed
```

Drivers are encouraged to add `media.md`, `protocol.md`, `troubleshooting.md`
when there's enough material. The docs site picks them up under
`/<repo>/<file>` automatically.

## What must NOT be in `docs/`

- `docs/.vitepress/` — the docs site owns VitePress config and theme.
- `docs/public/` — shared assets live in the docs site repo. Per-repo public
  assets that are tightly coupled to the package (e.g. driver-specific SVGs)
  may stay in `docs/public/<repo>/...` if absolutely necessary; coordinate
  with the docs site maintainer first.

## API reference

Run `pnpm docs:api` in your repo to regenerate `docs/api/` from typedoc.

The pre-push hook runs this automatically — if you haven't run it before
pushing, the hook will, and it will block the push if the regenerated content
differs from what's committed. Re-stage `docs/api/` and push again.

`docs/api/` is marked `linguist-generated=true` in `.gitattributes` so it
doesn't pollute language stats or PR diffs.

## Internal links

The docs site mounts each repo's `docs/` under `/<repo>/`. Use relative links
inside your `docs/` (`./hardware`, `../foo/index`) so they resolve under the
mounted path; absolute links (`/hardware`) won't work because the docs site
prepends the repo prefix.

Cross-package links use the full docs-site URL:
`https://thermal-label.github.io/contracts/`.

## How content gets pulled

The docs site runs `scripts/pull-driver-docs.mjs` before VitePress build:

1. Shallow `git clone` of each source repo into `.staging/<repo>/`.
2. `cp -r .staging/<repo>/docs/* docs/<repo>/`.
3. Verifies `index.md` exists; fails the build with a clear message otherwise.

The ref pulled is, in order:

1. The latest published version tag of that repo's primary package (e.g.
   `brother-ql-core-v0.3.0`).
2. Fallback: `main`.
3. Per-repo override via env var (for previewing unreleased docs).

If you restructure your `docs/` and the docs site build fails, the script
prints the missing file and the repo it expected. Don't rename `index.md`.

## Triggering a docs deploy

- `push` to `thermal-label.github.io/main` — content fix in the docs site.
- `repository_dispatch` from a source repo's release workflow — automatic
  rebuild after publish.
- `workflow_dispatch` — manual trigger from Actions tab.
- Nightly cron — backstop for `main` drift; off by default.
